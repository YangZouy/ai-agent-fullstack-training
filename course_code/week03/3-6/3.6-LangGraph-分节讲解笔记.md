## 第 0 讲 · 全局地图

### 0.1 本节到底要解决什么

一句话：**开发者提交一张上线工单，系统自动跑完 构建 → 单测 → 发布上线，中间该等人批的地方能停下来等人。**

这不是「调一次大模型」的问题，是**多步骤流程编排**的问题：有先后顺序、有并行、有分叉、有"停下等人"。

### 0.2 概念区分（P2 表格）

| 名称 | 解决什么 | 不解决什么 | 本课用法 |
|---|---|---|---|
| **LangGraph** | 用「状态 + 节点 + 边」把流程编排成可执行的图，调度分支/循环/中断/恢复 | 不帮你写 Prompt，不做模型抽象 | **主角** |
| LangChain | 模型客户端 + 消息类型 + 工具接口的统一封装 | 不管你怎么调度多步骤流程 | 配角：只用它的 `@tool` 和消息类型 |
| AgentScope | 另一套独立 Agent 框架 | 与 LangGraph 不是插件关系 | 知道即可，不装 |
| Dify | 可视化拖拽搭 Workflow 的平台 | 不适合「代码内编排 + 跨进程恢复」这类工程化要求 | 知道即可，不部署 |
| LangSmith / Langfuse | 观测平台，记录每次调用的 Trace | 不参与执行，不会让任务具备"中断后继续"的能力 | 可选接入，本章不依赖 |

**记忆口诀**：LangGraph 管**流程怎么走**，LangChain 管**单步怎么调**。

### 0.3 业务拆解：先拆流程，再写代码（P2–P3）

教材强调的核心难点：**不是 API 怎么调，而是业务步骤拆得对不对。**
动手前先明确四件事：哪些**串行**、哪些**并行**、哪里**分叉**、哪里**停下等人**。

拆出来的 7 个业务步骤：

1. **受理申请**：校验工单字段，准备上下文
2. **前置检查**：构建 / 单测 / 安全扫描 / 依赖审计（**可并行**）
3. **变更分级**：按 `patch_diff` 判 L / M / H
   - 判据：敏感词（auth、payment）+ 改动长度
   - 等级越高，审批越严
4. **审批**：按等级决定是否人工介入、几人介入
5. **预发部署 + 冒烟**：部署 staging，跑冒烟；失败 → 打回修订，重跑
6. **灰度推进**：10% → 50% → 100%；每段 SRE 确认 + 健康监控
7. **完成报告**：汇总审批与阶段结果；工单标记最终状态（成功 / 被拒 / 回滚）

### 0.4 业务概念 → LangGraph 对象（关键映射表）

| 业务概念 | LangGraph 对象 | 说明 |
|---|---|---|
| 工单本身（贯穿全流程的共享数据） | **State** | 一个随流程一路传递的字典，每个节点从它读数据、把结果写回它 |
| 每个步骤 | **节点**（一个 Python 函数） | 接收整个 state，返回要更新的字段 |
| 步骤之间的依赖关系 | **边**（`add_edge` / `add_conditional_edges`） | 决定下一步去哪 |
| 流程总装 | **图**（`StateGraph`） | 构建器，`compile()` 后才可执行 |
| 等待人工输入 | **Interrupt**（`interrupt()` + `Command(resume=...)`） | 暂停等审批 |
| 跨进程暂停与恢复 | **Checkpoint**（`SqliteSaver` / `AsyncSqliteSaver`） | 保存 state 快照 |
| 节点要调用的外部能力 | **ToolNode** | 拿着工具清单、负责并发执行工具的现成节点 |

### 0.5 一个必须先纠正的认知：节点 ≠ 一次模型调用

这是新手（包括有前端背景的同学）最容易卡住的地方。

- ❌ 错误理解：一个节点 = 调一次 LLM
- ✅ 正确理解：**节点 = 一个业务步骤**

节点内部做什么完全由你决定：
- 纯函数（算个数、拼个字符串）
- 调模型（真去问 LLM）
- 跑工具（调外部 API、跑 shell）

**看证据**：`demos/01_minimal/` 全程 7 个节点，**零 LLM 调用**，照样跑通。
所以这一章前几节根本不需要 API key——它讲的是编排，不是模型。

**前端类比**：
LangGraph 的「节点」更像 redux 里的 reducer / express 里的 middleware，
而不是「发一次 fetch 请求」。一个 middleware 里可以发请求，也可以什么都不发只改 ctx。

### 1.3 核心一：State 用 `TypedDict` 声明

```python
from typing import NotRequired, TypedDict

class ReleaseState(TypedDict):
    ticket_id: str
    service: str
    version: str
    checks_passed: int
    stages_completed: NotRequired[list[str]]
    outcome: NotRequired[str]
    report_path: NotRequired[str]
```

三个点，逐个讲：

**① `TypedDict` 是什么，为什么不用 `dict`？**

`TypedDict` 是 Python 的**类型标注**，用来描述「这个字典有哪些键、每个键是什么类型」。

关键认知：**它只在静态检查时生效，运行时完全不拦截。**

```python
state: ReleaseState = {"ticket_id": "T-1"}   # 少字段，运行时不报错
state["随便写的键"] = 123                     # 多字段，运行时也不报错
```

它真正的价值：
- IDE 自动补全 + 拼写检查（写错 `stages_complted` 会被类型检查器标红）
- 相当于给整个流程的「数据契约」写了一份文档，人和 AI 都能读

**前端类比**：`TypedDict` ≈ TypeScript 的 `interface`。
和 TS 一样，编译期检查，运行时是裸对象——所以别指望它帮你挡住脏数据。

**② `NotRequired` 是什么意思？**

| 字段 | 有没有 `NotRequired` | 含义 |
|---|---|---|
| `ticket_id` / `service` / `version` / `checks_passed` | 没有 | **入口必须提供**，流程启动时就得有 |
| `stages_completed` / `outcome` / `report_path` | 有 | **初始可缺省**，由后续节点逐步补上 |

看 `app.py` 怎么印证这一点：

```python
initial = {
    "ticket_id": ticket,
    "service": service,
    "version": version,
    "checks_passed": 0,      # 必填的 4 个，一个不少
    "stages_completed": [],  # 这个虽然 NotRequired，但节点里要做 + 运算，所以先给空列表
}
```

> ⚠️ 注意这个小细节：`stages_completed` 声明为 `NotRequired`，但 `app.py` 还是初始化了它。
> 为什么？看 `nodes.py`：`state["stages_completed"] + ["staging"]` —— 如果 key 不存在会 `KeyError`。
> **这是本 demo 里一个"声明可选但实际必须"的隐含约定**，属于代码里的小瑕疵，你读的时候要能看出来。

**③ 为什么叫「闭世界」？**

教材和提示词反复强调"闭世界，不要新增字段"。
意思是：State 就是节点之间**唯一的数据通道**，所有节点只能读写这里声明过的字段。
这样流程的所有数据流动都是可枚举、可审查的——这是工程化的前提，不是洁癖。

对比顶层 `release_pipeline/state.py`（79 行），字段多了 `patch_diff`、`messages`、`checks`、`approvals`、`canary_cursor` 等，
但原则一样：**任何节点不得引用此处未声明的字段**（该文件 docstring 原文）。

### 1.4 核心二：节点只返回「要更新的字段」

```python
def deploy_staging(state: ReleaseState) -> dict:
    return {"stages_completed": state["stages_completed"] + ["staging"]}
```

**这是 LangGraph 最反直觉的一条规则，值得单独讲。**

一个节点：
1. **接收整个 State**（`state: ReleaseState` —— 能读到所有字段）
2. **只返回增量**（`{"stages_completed": [...]}` —— 只写自己负责的那个字段）

#### 为什么不能返回整个 State？

教材给出的两个理由，我用大白话翻译一下：

**场景**：假设以后有两个节点并行跑（第 3 讲会出现真实的并行），都要改 `stages_completed`。

- **如果每个节点都返回整个 state**
  → A 返回 `{...整个副本，stages=[x]}`，B 返回 `{...整个副本，stages=[y]}`
  → 框架不知道该听谁的
  → **没有 reducer：后写的覆盖先写的，A 的修改丢了**
  → **有 reducer：两份整个副本被合并，字段被重复计算**

- **如果每个节点只返回自己的增量**
  → A 返回 `{"stages_completed": ["a"]}`，B 返回 `{"stages_completed": ["b"]}`
  → 框架清楚地知道：这两份都是针对同一字段的增量
  → 按字段合并规则处理，不会丢

#### 和普通 pipeline 的区别（这个对比很重要）

| | 普通 pipeline | LangGraph |
|---|---|---|
| 传递方式 | 全量对象往下传 | 节点报增量，框架统一合并 |
| 能否并行 | 不行，一环扣一环 | **可以并行** |
| 能否重跑 | 不行 | **可以重跑**（有 checkpoint） |
| 每步存档 | 没有 | **每步存快照**（为 interrupt 恢复做准备） |

**一句话**：因为 LangGraph 要支持「并行 + 重跑 + 存档」，所以节点必须报增量，不能报全量。

#### 前端类比

这跟 React 的 `setState` 是一个道理：

```js
// React：传增量，框架帮你 merge
setState({ count: 1 })          // ✅ 只改 count

// 如果你这么写
setState(wholeNewObject)        // ⚠️ 整个替换，容易覆盖掉别人刚改的
```

也跟 Git 的 patch 一样：提交的是 diff，不是整个仓库的快照。

#### `finalize` 节点：唯一有副作用的

```python
def finalize(state: ReleaseState) -> dict:
    reports_dir = Path(os.environ.get("REPORTS_DIR", "./reports"))
    reports_dir.mkdir(parents=True, exist_ok=True)
    path = reports_dir / f"{state['ticket_id']}.json"
    path.write_text(json.dumps({...}, ensure_ascii=False, indent=2), encoding="utf-8")
    return {"outcome": "released", "report_path": str(path)}
```

注意它干了两件事：
1. **副作用**：写文件到磁盘
2. **返回增量**：`outcome` 和 `report_path`

> 🔖 **这里埋一个伏笔**，第 4 讲会重点讲：
> `finalize` 写文件是安全的，因为它**不在 `interrupt()` 之前**。
> 但如果你把写文件/部署/扣款放在 `interrupt()` 之前，恢复时会被**重复执行**。
> 先记住这句话：**`interrupt()` 之前禁止副作用。** 第 4 讲展开。

另外注意 `os.environ.get("REPORTS_DIR", ...)` —— 用环境变量控制输出目录，是为了让测试能把报告写到临时位置，不污染工程目录。这是个好习惯。

### 1.5 核心三：图 = 构建器 + `compile()`

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph

def build_graph(checkpointer=None):
    builder = StateGraph(ReleaseState)          # ① 声明这张图用什么 State
    builder.add_node("intake", nodes.intake)    # ② 注册节点：名字 → 函数
    builder.add_node("deploy_staging", nodes.deploy_staging)
    # ... 其余 5 个
    builder.add_edge(START, "intake")           # ③ 连边
    builder.add_edge("intake", "deploy_staging")
    # ...
    builder.add_edge("finalize", END)
    return builder.compile(checkpointer=checkpointer or InMemorySaver())  # ④ 编译
```

四步拆解：

**① `StateGraph(ReleaseState)` —— 告诉图用什么数据结构**
后面所有节点的读写都受这个类型约束。

**② `add_node(名字, 函数)` —— 注册节点**
名字是字符串，边通过名字引用节点，而不是直接引用函数对象。
好处：图的结构（边）和节点的实现（函数）解耦，改边不用改节点。

**③ `add_edge(从, 到)` —— 连边**
`START` 和 `END` 是框架提供的两个**虚拟节点**，标记入口和出口。
这一节**全部用普通边**，一次 `add_conditional_edges` 都没出现（第 2 讲才加）。

**④ `compile()` —— 编译成可执行对象**

```python
builder = StateGraph(ReleaseState)   # builder：还在搭，不能跑
graph = builder.compile(...)         # graph：能 invoke / stream 了
```

三个要点：
- `compile()` **只做结构检查**（有没有孤岛节点、边指向不存在的节点），**不查业务规则**
- 必须传 `checkpointer`，否则后面 `Command(resume=...)` 会直接报错
- `checkpointer` 负责**每步存 State 快照**，这是 interrupt 能恢复的物理基础

**这一节的 checkpointer 是 `InMemorySaver()`** —— 存内存里，进程一退出就没了。
第 4 讲会换成 `SqliteSaver`，才能跨进程恢复。

**为什么这一节就要 checkpointer？**
教材原话：「每步存 State 快照，为后续 interrupt 恢复做准备」。
现在存了，第 4 讲加 interrupt 时不用改结构——这就是「先跑通主线，后续逐步叠加」的收益。

### 1.6 `app.py`：怎么观察这个流程

```python
cfg = {"configurable": {"thread_id": ticket}}
async for ev in graph.astream(initial, config=cfg, stream_mode="updates"):
    for node, delta in ev.items():
        print(f"▶ {node}: {delta}")
final = await graph.aget_state(cfg)
print("\n终态：", final.values)
```

四个 API 逐个讲：

| API | 作用 | 前端类比 |
|---|---|---|
| `astream(...)` | 异步流式执行，`async for` 逐节点取事件 | SSE / `fetch` 的 ReadableStream 逐 chunk 读 |
| `stream_mode="updates"` | 每个事件只给**本节点的 state 增量** | 每个 chunk 只有 diff，不是全量 |
| `config={"configurable": {"thread_id": ...}}` | 给这次运行编号（存档名） | 类似 sessionId / requestId |
| `aget_state(cfg)` | 取最终完整快照 | 拉取最终状态 |

**`stream_mode="updates"` 为什么好用？**
它给的是 `{节点名: 该节点返回的增量}`，正好对应我们「节点只返回增量」的设计——
所以你能一眼看出**每个节点到底改了什么**。这就是教材里那 7 行 `▶` 输出的来源。

实际输出（教材 P6）：

```
▶  intake: {'checks_passed': 4, 'stages_completed': []}
▶  deploy_staging: {'stages_completed': ['staging']}
▶  smoke_test: {'stages_completed': ['staging', 'smoke']}
▶  canary_10: {'stages_completed': ['staging', 'smoke', 'canary_10']}
▶  canary_50: {'stages_completed': [..., 'canary_50']}
▶  canary_100: {'stages_completed': [..., 'canary_100']}
▶  finalize: {'outcome': 'released', 'report_path': '.../reports/DEMO-01.json'}
```

对着这 7 行看三件事：
1. **节点按边顺序推进** —— 和 `graph.py` 里 `add_edge` 的顺序完全一致
2. **State 增量可见** —— `stages_completed` 一项一项往上加
3. **主线发布成功** —— 最后 `outcome="released"`

### 1.7 验收测试 = 「什么叫做完了」

教材的方法论很值得学：**把验收标准（AC）写成可执行的 pytest 用例，以测试全部通过为准。**

```python
def test_ac2_stages_in_order():
    out = _drive("01-AC2")
    assert out["stages_completed"] == [
        "staging", "smoke", "canary_10", "canary_50", "canary_100",
    ]
```

4 条 AC：

| AC | 断言 | 验证了什么 |
|---|---|---|
| AC-1 | `outcome == "released"` | 流程能跑到终点 |
| AC-2 | `stages_completed == [...5 项...]` | **顺序正确**（不只是都执行了） |
| AC-3 | `checks_passed == 4` | 节点内的计算逻辑对 |
| AC-4 | `Path(report_path).exists()` | 副作用（写文件）真的发生了 |

注意 AC-2 断言的是**列表顺序**，不是集合——因为「顺序」本身就是业务规则（先预发后灰度）。

测试里的两个技巧：
```python
os.environ["REPORTS_DIR"] = str(ROOT / "reports")   # 环境变量控制输出位置
...
Path(out["report_path"]).unlink()                    # 测完删掉，不留脏数据
```

## 第 1 讲 自测参考答案

> 先自己想再看。下面给出答案与延伸解释。

**1. TypedDict 运行时会拦截未声明的键吗？**
不会。`TypedDict` 是纯静态类型标注，运行时就是普通 `dict`。
多写键、少写键都不会报错。它的价值在 IDE 补全、拼写检查，以及给 AI/协作者一份可读的数据契约。
（真正会报错的是 `KeyError` —— 你读了不存在的键，比如 `state["stages_completed"]`。）

**2. `return state` 在线性流程能跑通吗？并行场景呢？**
- 线性流程：**能跑通**。每次只有一个节点在写，返回全量只是「把原样再写一遍」，结果正确。
  这也是为什么这个错误很容易被掩盖 —— 本地跑得好好的。
- 并行场景：**会出问题**。两个节点各自返回整份 state 副本，框架要么后写覆盖先写（无 reducer），
  要么重复合并（有 reducer），修改丢失或翻倍。

**3. 注释掉 `add_edge("canary_10", "canary_50")` 会怎样？**
`compile()` **不报错** —— 它只检查结构完整性（边指向的节点存不存在），
`canary_50` 仍被 `add_node` 注册过，只是没有入边。
跑起来：`canary_10` 执行完，图发现没有下一步，直接结束。
终态 `stages_completed == ["staging", "smoke", "canary_10"]`，`outcome` 为 None（没走到 finalize）。
这正是「compile 只查结构、不查业务」的活证据：**图能编译 ≠ 流程正确**，所以必须用 AC 测试兜住业务。

**4. 为什么这一节就要传 `thread_id`？**
- `thread_id` 是 checkpointer 存/取快照的**键**。没有它，`InMemorySaver` 不知道这份快照属于谁。
- 提前把「一次运行 = 一个 thread」的约定立起来，第 4 讲换 SQLite + 加 interrupt 时，`get_state(cfg)` / `Command(resume=...)` 可以直接用，不用回头改调用方式。

注意 `thread_id` **不是操作系统线程**，是「一次独立任务的编号」，相当于存档名。
它只是查找键，不是权限控制 —— 真正的审批权限还得入口自己校验（第 4 讲会再强调）。

# 第 2 讲 · 条件路由 `demos/02_routing/`（PDF P8–P11）

> 上一讲我们拿到一张能跑通的直线图，但它有个致命缺陷。
> 这一讲加**条件路由**：先给变更分级，再按等级走不同审批路径。
> 对应代码：`demos/02_routing/`（state.py 17 行 / nodes.py 79 行 / graph.py 51 行 / app.py 40 行）

## 2.1 为什么必须加分支

第 1 讲那张图的问题：**改一行 README 和改 `auth` 模块，走的是同一条路。**

这两者的风险差了几个数量级，却享受完全相同的审批强度——真实工程里不可接受。
所以业务上必须先**分级**，再按等级走不同的审批路径。

教材的做法：在 `intake` 之后插一步**变更分级**，依据工单里的 `patch_diff`（代码改动内容）
判 L / M / H，然后按等级路由到不同审批节点。

## 2.2 State 新增了什么（对比 01）

| 字段 | 变化 | 说明 |
|---|---|---|
| `patch_diff: str` | 🆕 入口必填 | 分级判据的来源，没有它就没法判级 |
| `change_level: NotRequired[Literal["L", "M", "H"]]` | 🆕 | 由 `classify_change` 写入，路由函数读它 |
| `approver_count: NotRequired[int]` | 🆕 | 由三个审批节点写入，报告里要带 |

```python
class ReleaseState(TypedDict):
    ticket_id: str
    service: str
    version: str
    patch_diff: str                                   # 新增，入口必填
    checks_passed: int
    change_level: NotRequired[Literal["L", "M", "H"]]  # 新增
    approver_count: NotRequired[int]                   # 新增
    stages_completed: NotRequired[list[str]]
    outcome: NotRequired[str]
    report_path: NotRequired[str]
```

注意 `change_level` 的类型是 `Literal["L", "M", "H"]` 而不是 `str` —— **这是本讲重点，见 2.6**。

## 2.3 分级节点：判断顺序就是业务决策

```python
def classify_change(state: ReleaseState) -> dict:
    diff = state.get("patch_diff", "")
    lowered = diff.lower()
    if any(k in lowered for k in ("auth", "payment", "password", "token")):
        level: Literal["L", "M", "H"] = "H"
    elif len(diff) > 800:
        level = "M"
    else:
        level = "L"
    return {"change_level": level}
```

三条判据，**但顺序是关键**：敏感词优先于长度。

> **本讲第一个警觉点**：如果把 `len(diff) > 800` 写在前面，
> 一个「900 字的 auth 改动」会被判成 **M** 而不是 **H** ——
> 风险最高的变更反而走了宽松通道。**规则顺序本身就是业务决策，不是实现细节。**

另外两个细节：

- `diff.lower()` 让 `AUTH` / `Auth` / `auth` 都能匹配（大小写不敏感）
- 这里用 `state.get("patch_diff", "")`，第 1 讲的 `stages_completed` 却用 `state["..."]`。
  前者是防御性写法（缺了降级为空串 → 判 L），后者直接 `KeyError`。
  **同一工程里两种风格并存**，读代码时要能看出来；自己写时建议统一。

## 2.4 分支结构（文字图）

```
                          ┌── L ──→ approval_auto_L   (approver_count = 0) ─┐
START → intake → classify_change ── M ──→ approval_lead_M   (count = 1) ─┼──→ deploy_staging → smoke → canary_10/50/100 → finalize → END
                          └── H ──→ approval_dual_H   (count = 2) ─┘
```

要点：**三条路运行时只走一条**；走完之后**汇合到同一个 `deploy_staging`**。

## 2.5 `add_conditional_edges` 的三个参数

```python
def route_by_level(state: ReleaseState) -> Literal["L", "M", "H"]:
    return state["change_level"]

builder.add_conditional_edges("classify_change", route_by_level, {
    "L": "approval_auto_L",
    "M": "approval_lead_M",
    "H": "approval_dual_H",
})
```

| 参数 | 名字 | 作用 |
|---|---|---|
| `source` | 分叉点 | 这个节点**执行完之后**才开始选路 |
| `path_fn` | 选路函数 | 只读 State，返回**路名** |
| `path_map` | 映射表 | 路名 → 节点名 |

### 三条纪律

**① 路由函数不改状态；要改 State 就专门加节点。**
这就是为什么「判级」必须是独立节点 `classify_change`，而不能塞进 `route_by_level` 里 ——
`route_by_level` 只是个**读取器**，它唯一的工作是把已经算好的 `change_level` 念出来。

> 类比：`classify_change` 是**计算属性**，`route_by_level` 是 **switch 的条件表达式**。别混在一起。

**② 返回类型用 `Literal[...]` —— 它是图元信息，不是装饰。**（见 2.6）

**③ 分叉点必须接在「已经算出结论」的节点之后。**
先算后选，选路时不做计算。

## 2.6 为什么 `Literal[...]` 不是装饰

教材专门讲这一点，也最容易被忽略。同一个图，只改返回类型注解：

**返回 `Literal["L","M","H"]`** —— 框架编译期就能枚举出分支集合，Mermaid 画出带标签的边：

```
classify_change --L--> approval_auto_L
classify_change --M--> approval_lead_M
classify_change --H--> approval_dual_H
```

**返回 `str`** —— 能编译、能跑，但分支标签丢失：

```
classify_change --> approval_auto_L
classify_change --> approval_lead_M
classify_change --> approval_dual_H
```

差别在哪：

- `Literal` 把「可能走哪几条路」变成了**编译期已知的元信息**，供 `compile()` 与 Mermaid 使用
- 用 `str` 图照样能跑，但**你画出来的流程图看不出哪条边对应哪个等级** ——
  等业务复杂到十几个分支时，这张图就失去排查价值了

> 前端类比：这就像给 API 响应写 `type Status = "L" | "M" | "H"` 而不是 `string`。
> 运行时都能跑，但前者让 IDE 和类型检查器能帮你发现拼错的路名，后者只能等运行时炸。

## 2.7 分支末端怎么汇合

```python
builder.add_edge("approval_auto_L", "deploy_staging")
builder.add_edge("approval_lead_M", "deploy_staging")
builder.add_edge("approval_dual_H", "deploy_staging")
```

**三条普通边指向同一个目标 = 汇合。** LangGraph 里没有专门的「join 节点」概念，
汇合就是多条边指向同一节点。

## 2.8 路由分支 ≠ 并行（为第 3 讲铺垫）

教材 P11 明确区分了两种「多」，别混为一谈：

| | 条件分支（本讲） | ToolNode 并行（第 3 讲） |
|---|---|---|
| 运行时行为 | 三条路**只走一条** | 一个节点**内部**并发执行多个工具 |
| 图上表现 | 三条可见的边 | **只是一个普通节点** |
| 谁决定 | 路由函数读 State | `messages` 末尾 AIMessage 里的 `tool_calls` |

## 2.9 跑起来验证

`app.py` 一次跑三个 case，演示三条路径：

```python
cases = [
    ("R-02-L", "tiny config tweak"),              # 短 → L
    ("R-02-M", "x" * 1200),                       # 长度 1200 > 800 → M
    ("R-02-H", "modify auth token rotation logic"),  # 含 auth/token → H
]
```

输出（教材 P10）：

```
R-02-L: ▶ classify_change: {'change_level': 'L'} → ▶ approval_auto_L:  {'approver_count': 0}
R-02-M: ▶ classify_change: {'change_level': 'M'} → ▶ approval_lead_M:  {'approver_count': 1}
R-02-H: ▶ classify_change: {'change_level': 'H'} → ▶ approval_dual_H:  {'approver_count': 2}
→ 4 passed in 0.21s
```

### 4 条 AC

| AC | 断言 | 验证了什么 |
|---|---|---|
| AC-1 | 短 diff → `L`、`approver_count==0`、`outcome=="released"` | 自动放行路径通 |
| AC-2 | 长度 1200 的 diff → `M`、`approver_count==1` | 长度判据生效 |
| AC-3 | 含 `auth token` 的 diff → `H`、`approver_count==2` | 敏感词判据生效且优先 |
| AC-4 | **三种 diff 都必须把 `stages_completed` 走完** | **分支不能吃掉主线** |

AC-4 是本讲的验收关键：加了分叉之后，必须仍有测试保证**每一条路都能走到终点**。
只测「H 走了对的路」是不够的 —— 分支改坏了主线，前三条 AC 可能照样过。

## 2.10 本讲收口

| # | 认知 |
|---|---|
| 1 | 先算后选：`classify_change` 算结论，`route_by_level` 只读取 |
| 2 | 路由函数只读 State 不改 State；要改就加节点 |
| 3 | `Literal[...]` 是图元信息，供 `compile()` 与 Mermaid 用，不是装饰 |
| 4 | 汇合 = 多条边指向同一节点，没有专门 join 节点 |
| 5 | 条件分支「只走一条」≠ ToolNode「节点内并发」 |
| 6 | 加分支后必须有 AC 守住「主线仍完整」 |
| 7 | 规则判断的 if/elif 顺序是业务决策，不是实现细节 |

## 第 2 讲 自测参考答案

**2. 不建议。** 两个理由：
- 职责上：路由函数是**读取器**，改 State 是节点的事。塞进去之后，

所以类型注解要当作文档来维护，不是给 type checker 交差。

**4. 不算并行。** 运行时三条边**只有一条会被走**——`route_by_level` 只返回一个键，

# 第 3 讲 · 并行 `demos/03_toolnode/`（PDF P11–P15）

> 上一讲主线 + 分支就位，但前置检查还是 `intake` 里内联的 4 个假函数，而且是**串行**的。
> 这一讲把 4 项检查升级为真工具并行：LangGraph 现成的 `ToolNode`。
> 对应代码：`demos/03_toolnode/`（state.py 32 / tools.py 40 / nodes.py 121 / graph.py 56 / app.py 37）

## 3.1 为什么需要并行

第 2 讲的 `intake` 是这么"跑检查"的：

```python
def _run_one_check(name: str) -> bool:
    return True          # 假的，直接返回 True
```

四个检查是**内联假函数**，而且是**串行**的。真实工程里构建、单测、安全扫描、依赖审计
**互不依赖**，串行跑 = 4 倍耗时。

需求很直白：**互不依赖的子任务同时开工**。LangGraph 给的现成答案是 `ToolNode` ——
你提供工具清单，它负责并发执行。

## 3.2 新增 `tools.py`：`@tool` 到底干了什么

```python
from langchain_core.tools import tool

@tool
def build_service(service: str, version: str) -> str:
    """构建服务镜像。"""
    return json.dumps({"tool": "build", "passed": True, "summary": "..."})

CHECK_TOOLS = [build_service, run_unit_tests, security_scan, dependency_audit]
```

`@tool` 装饰器干了三件事 —— **它把一个 Python 函数翻译成一段发给模型的 JSON Schema**：

| 你写的 | 翻译后（HTTP 请求体里的 `tools` 数组） |
|---|---|
| 函数名 `build_service` | `"name": "build_service"` |
| docstring `"构建服务镜像。"` | `"description": "构建服务镜像。"` ← **给模型看的** |
| 类型注解 `service: str` | `"parameters": {"service": {"type": "string"}}` |
| 返回值 `-> str` | 工具结果必须是字符串（所以用 `json.dumps`） |

等价于你手写这段发到网线的东西：

```json
{
  "type": "function",
  "function": {
    "name": "build_service",
    "description": "构建服务镜像。",
    "parameters": {
      "type": "object",
      "properties": {"service": {"type": "string"}, "version": {"type": "string"}},
      "required": ["service", "version"]
    }
  }
}
```

> **两个容易踩的点**：
> 1. **docstring 不是注释，是 prompt 的一部分。** 写错或写空，模型就不知道什么时候该调这个工具。
> 2. **返回值必须是字符串。** 所以四个工具都 `json.dumps(...)` —— 工具结果要塞进
>    `ToolMessage.content`，而消息内容是字符串。这也是后面 `collect_checks` 要 `json.loads` 反解的原因。

## 3.3 State 新增两个字段

```python
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages

class ReleaseState(TypedDict):
    ...
    messages: NotRequired[Annotated[list[AnyMessage], add_messages]]   # 新增
    checks:   NotRequired[list[CheckResult]]                            # 新增
```

`Annotated[list[AnyMessage], add_messages]` 是本讲**最核心的一行**，见 3.7。

## 3.4 `intake` 的变化：手写一条 `AIMessage`

```python
def intake(state: ReleaseState) -> dict:
    fanout = AIMessage(
        content="",
        tool_calls=[
            {"name": "build_service",    "args": {...}, "id": "call_build"},
            {"name": "run_unit_tests",   "args": {...}, "id": "call_unit"},
            {"name": "security_scan",    "args": {...}, "id": "call_scan"},
            {"name": "dependency_audit", "args": {...}, "id": "call_audit"},
        ],
    )
    return {"messages": [fanout], "stages_completed": []}
```

**本讲最容易误解的一点：`intake` 里没有调用任何模型。**

`AIMessage` 是我们**手写的**，不是模型返回的。那 4 个 `tool_calls` 正常情况下应该由模型
读完问题后自己决定 —— 这里我们**越俎代庖直接指定**。

对照真实场景里模型返回的 assistant 消息：

```json
{
  "role": "assistant",
  "content": "",
  "tool_calls": [
    {"id": "call_build", "type": "function",
     "function": {"name": "build_service",
                  "arguments": "{\"service\":\"auth-svc\",\"version\":\"1.0.0\"}"}}
  ]
}
```

`AIMessage(tool_calls=[...])` 就是这段 JSON 的 Python 对象形式。
**用 mock 手写它，是为了在没有 API key、不花 token 的情况下把编排逻辑跑通** ——
这正是教材"前几节零 LLM 调用"的设计意图。

工具结果回传时，对应的是这条消息：

```json
{"role": "tool", "tool_call_id": "call_build", "content": "{\"tool\":\"build\",...}"}
```

也就是 Python 里的 `ToolMessage(content=..., tool_call_id=...)`。

## 3.5 `ToolNode` 的契约：四步

1. 取 `messages` 末尾那条 `AIMessage`
2. 按 `tool_calls` 的 `name` 找到对应工具
3. **并发执行 4 个工具**（并行就来自这一步）
4. 结果包成 `ToolMessage` 追加回 `messages`

```python
from langgraph.prebuilt import ToolNode
from tools import CHECK_TOOLS

builder.add_node("tool_checks", ToolNode(CHECK_TOOLS))   # 一个节点对象，不是函数
builder.add_edge("intake", "tool_checks")
builder.add_edge("tool_checks", "collect_checks")
```

要点：

- **`ToolNode` 是现成的节点对象，你不用写函数。** 它是本章唯一一个"不是你写的函数"的节点。
- **ToolNode 不看图，只看 `messages` 末尾的 `AIMessage`。**
  一条 `AIMessage` 携带 4 个 `tool_calls` → 自动并发执行 4 个工具 →
  结果包成 `ToolMessage` 追加回 `messages`。**这就是 ToolNode 的契约。**

**与第 2 讲条件分支的对比（重要）：**

| | 条件分支（第 2 讲） | ToolNode 并行（本讲） |
|---|---|---|
| 图上表现 | 三条可见的边 | **只是一个普通节点** |
| 运行时 | 三条路**只走一条** | **一个节点内部**跑 4 件事 |
| 谁决定 | 路由函数读 State | `messages` 末尾 AIMessage 里的 `tool_calls` |

→ 所以你在 Mermaid 图上**看不到 4 条并行线**，它藏在 `tool_checks` 这个节点里。

## 3.6 `collect_checks`：把消息解析回结构化数据

```python
def collect_checks(state: ReleaseState) -> dict:
    results: list[CheckResult] = []
    for msg in state.get("messages", []):
        if not isinstance(msg, ToolMessage):
            continue
        try:
            payload = json.loads(msg.content)
        except (TypeError, json.JSONDecodeError):
            payload = {"tool": msg.name, "passed": False, "summary": str(msg.content)}
        results.append(CheckResult(
            name=payload.get("tool", msg.name or "unknown"),
            passed=bool(payload.get("passed", False)),
            summary=payload.get("summary", ""),
        ))
    return {"checks": results, "checks_passed": sum(1 for r in results if r["passed"])}
```

做的事：**遍历整个 `messages`，挑出所有 `ToolMessage`，`json.loads` 反解，聚成 `checks` 列表。**

注意那个 `try/except`：工具如果返回非 JSON（比如真的抛异常返回了错误文本），
这里降级成 `passed=False` 而不是崩溃。
**这是"工具可能失败"这件事的第一个显式处理** —— 真实工程里安全扫描挂了，
你不希望整条流水线崩掉。

## 3.7 为什么 `messages` 必须挂 `add_messages` reducer（本讲核心）

**reducer = 多个节点写同一字段时，决定"新旧值怎么合并"的规则。**

- **不加 reducer**：默认 `replace` —— 后写的覆盖先写的
- **`add_messages`**：**追加** + 按消息 id **去重**

### 本机实测证据（已验证）

把 `state.py` 里 `Annotated[list[AnyMessage], add_messages]` 改成 `list[AnyMessage]`，
其他一行不动，跑同一个流程：

| | `messages` 最终内容 | 4 条 AC |
|---|---|---|
| 有 `add_messages` | `[AIMessage, ToolMessage×4]` → **5 条** | 4 passed |
| 去掉 reducer | `[ToolMessage×4]` → **4 条，AIMessage 没了** | **4 passed（照样全过！）** |

**这是本章第三次"跑通 ≠ 可靠"，而且是最狠的一次：测试全绿，但 `messages` 通道已被破坏。**

为什么现在看不出问题？因为 `ToolNode` 是**先读后写** —— 它读 AIMessage 的时候 AIMessage 还在，
写完才覆盖；`collect_checks` 只关心 `ToolMessage`，也不受影响。

什么时候会炸？**第二轮 tool call。** 真实场景里模型看到工具结果后还要再发一轮 `tool_calls`，
那时 `messages` 里已经没有历史上下文了。教材原文：*"不加 reducer：`intake` 的 `AIMessage` 会被后续节点覆盖"*。

> 前端类比：`add_messages` 就像 Redux 里给某个 action 写的 reducer。
> 默认 reducer 是 `(state, payload) => payload`（整个替换），
> 而消息列表需要的是 `(state, payload) => [...state, ...payload]`（追加）。
> **不加 reducer 字段就是被整体替换，不是追加。**

### 另一条规则：写 messages 是"加一条"，不是"换一批"

- `{"messages": [fanout]}` → 追加到列表末尾
- 再发 `tool_calls` 时注意：用**新 id**，或显式清空（`RemoveMessage`）
- `collect_checks` 保留全部消息 —— **审计需要**，别为了省内存把历史删了

## 第 3 讲 自测参考答案

**1. 为什么必须 `json.dumps` 返回？**
`ToolMessage.content` 是字符串字段 —— 工具结果最终要作为消息内容回传给模型，
而 HTTP 请求体里 `{"role":"tool","content": ...}` 的 content 就是字符串。
所以工具函数必须返回可序列化的字符串，下游 `collect_checks` 再 `json.loads` 反解。
直接返回 dict 会在构造 `ToolMessage` 时出问题（或至少丢结构）。

**2. `AIMessage` 是谁产生的？**
是我们**手写构造**的，不是模型返回的。本讲**零 LLM 调用**。
真实场景里这 4 个 `tool_calls` 由模型输出，这里是为了无 key、零成本跑通编排逻辑。
关键认知：**LangGraph 不关心这条 AIMessage 是人写的还是模型写的**，
它只看 `messages` 末尾有没有带 `tool_calls` 的 AIMessage。

**3. 补一条能抓住 bug 的断言：**

```python
def test_ac5_ai_message_preserved():
    out = _drive("03-AC5", "tiny")
    msgs = out.get("messages", [])
    assert any(type(m).__name__ == "AIMessage" for m in msgs), "AIMessage 被覆盖了"
    assert len(msgs) == 5, f"应为 1 条 AIMessage + 4 条 ToolMessage，实际 {len(msgs)}"
```

去掉 reducer 后 `len(msgs)` 变成 4 且没有 AIMessage → 立刻红。
→ 这正是「AC 要覆盖到机制本身，而不只是覆盖到结果」的例子：
原 AC-4 断言的是**结果**（有 4 条 ToolMessage），新断言的是**通道**（AIMessage 还在）。

**4. 为什么要遍历整个 `messages` 而不是只看最后 4 条？**
- 健壮性：工具可能失败、可能只回了 3 条，"取最后 4 条"会取错
- 通用性：如果有多个 ToolNode 轮次，`ToolMessage` 会散落在列表不同位置
- 顺序无关：`isinstance(msg, ToolMessage)` 过滤不依赖位置，不怕将来插入别的消息

代价是：如果历史里残留了**上一轮**的 ToolMessage（比如第 5 讲的修订循环回到 `intake` 重跑），
会被重复统计。教材里顶层 `state.py` 的注释专门处理了这点 ——
`checks` 用 **replace 语义**（`begin_revision` 后由下一轮 `collect_checks` 整体覆盖），
而不是 add。**第 5 讲会回到这个问题。**

**5. 加第 5 个工具要改哪些地方？**
只改 `tools.py` 不够，至少四处：

| 位置 | 改什么 |
|---|---|
| `tools.py` | 新增 `@tool def license_check(...)`，并加进 `CHECK_TOOLS` 列表 |
| `nodes.py::intake` | `tool_calls` 里加第 5 项（**忘了这步 → 新工具永远不会被调用**） |
| `tests/` | AC-1 的 `len(checks) == 4` 要改成 5，名字集合要加 `"license_check"` |
| `state.py` | 本层 `CheckResult.name` 是 `str` 不用改；但顶层 `state.py` 用的是 `Literal[...]`，**那边必须加** |

最容易漏的是 **`intake` 里的 `tool_calls`** —— 因为工具清单（`CHECK_TOOLS`）和
调用指令（`tool_calls`）是**两个独立的地方**，`ToolNode` 只会执行 `tool_calls` 里列出来的，
注册了但没调用的工具就是摆设。这也是"手写 AIMessage"这种 mock 方式特有的隐患：
真实场景里模型会自己决定调哪些，不存在这个问题。

## 4.1 现在缺什么

```python
def approval_lead_M(state: ReleaseState) -> dict:
    return {"approver_count": 1}      # 直接返回，根本没等人
```

真实场景：M 级等 Tech Lead 批，H 级要 Tech Lead + Security **串两道**。
而且 H 级审批可能**跨天** —— 进程必须能停得下来、重启接得上。

这一讲加三个东西：

1. 审批节点改真 `interrupt()`
2. `Command(resume=...)` 送回人工决定
3. `InMemorySaver` → **SQLite Checkpointer**，支持跨进程

## 4.2 State 新增 `approvals`

```python
class Approval(TypedDict):
    interrupt_id: Literal["INT-1", "INT-2A", "INT-2B"]
    role: Literal["tech_lead", "security"]
    action: Literal["approve", "reject"]
    actor: str
    feedback: str

class ReleaseState(TypedDict):
    ...
    approvals: NotRequired[Annotated[list[Approval], add]]   # add reducer
```

注意用的是 **`add`**（`from operator import add`），不是 `add_messages`：

| reducer | 语义 | 用在哪 |
|---|---|---|
| `add_messages` | 追加 + 按消息 id 去重（消息专用） | `messages` |
| `add` | 列表直接拼接（通用） | `approvals`、`metric_samples` |

**为什么用 `add`？** 每个审批节点只返回**自己那一条**，框架累加成完整审计轨迹。
这样 `route_after_approval` 就能用 `any(a["action"]=="reject")` 一眼看出有没有人拒。

## 4.3 `interrupt()` 靠什么"停"

```python
def approval_m(state: ReleaseState) -> dict:
    decision = interrupt({
        "interrupt_id": "INT-1",
        "role": "tech_lead",
        "ticket_id": state["ticket_id"],
        "diff_preview": state.get("patch_diff", "")[:300],   # 只给前 300 字符
        "actions": ["approve", "reject"],
    })
    return {"approver_count": 1,
            "approvals": [_as_approval(decision, "INT-1", "tech_lead")]}
```

`interrupt(payload)` **抛出一个特殊信号**让图停下。`payload` 是给审批人看的可 JSON 化数据 ——
注意 `diff_preview[:300]`，diff 可能有几万字符，全塞进 payload 既浪费也难读。

**这个函数会被执行两遍，而且两遍行为不同：**

| | 首次执行 | 恢复执行 |
|---|---|---|
| 1 | 节点开始执行 | 节点**从头**重新执行 |
| 2 | `interrupt(payload)` 抛出信号 | `interrupt()` **返回 resume 的值** |
| 3 | 图暂停，checkpoint 落盘 | 往下走：`_as_approval` 组装 |
| 4 | `return` —— **没执行到** | 执行 `return`，写回 State |

## 4.4 恢复：用 `Command(resume=...)`，不是重提交

```python
snap = graph.get_state(cfg)
if not snap.next:
    print("该工单没在等待审批。")
    return
graph.invoke(
    Command(resume={"action": action, "actor": actor, "feedback": feedback}),
    config=cfg,
)
```

两个要点：

- **恢复 ≠ 重跑任务。** `Command(resume=...)` 是把人工决定**送回**那个卡住的节点，从头重跑它。
- **必须由"收到人工决定"的入口触发。** 教材明确要求：不能 submit 之后自动批准。

`_as_approval()` 把 resume 回来的 dict 规整成 `Approval` ——
注意它把非 dict、非法 action **一律降级成 `reject`**：

```python
action = d.get("action", "approve")
if action not in ("approve", "reject"):
    action = "reject"
```

**默认拒绝而不是默认放行**，这是安全侧的正确取向。

## 4.5 Checkpointer：内存换成 SQLite

```python
@contextmanager
def open_checkpointer():
    db_path = Path(os.environ.get("CHECKPOINT_DB", "./checkpoints_04.sqlite")).resolve()
    db_path.parent.mkdir(parents=True, exist_ok=True)
    with SqliteSaver.from_conn_string(str(db_path)) as saver:
        yield saver
```

两个细节值得学：

- **`@contextmanager`**：保证 `with` 退出时 SQLite 连接被正确关闭。DB 连接是资源，不能靠 GC。
- **路径走环境变量**：测试可以指向临时 DB，不会互相污染
  （这是教材第 9 章"复用旧 checkpoint 污染测试"的正面解法）。

`graph.py` 的对应变化：

```python
def build_graph(checkpointer):        # 不再是 checkpointer=None
    ...
    return builder.compile(checkpointer=checkpointer)   # 必须传
```

**第 1 讲那句"必须传 checkpointer"在这里兑现了** —— 没有它，`Command(resume=...)` 会直接报错。

## 4.6 `thread_id` 是什么（必须澄清）

```python
cfg = {"configurable": {"thread_id": ticket}}
```

**`thread_id` 不是操作系统线程。** 它是"一次独立任务的编号"，相当于**存档名**。

- 同 DB 文件 + 同 `thread_id` → 任何进程、任何时刻都能 `get_state()` 找回
- **`thread_id` 只是查找键，不是权限**。教材特意提醒：真正的审批权限还得入口自己校验

> 前端类比：`thread_id` 就像 localStorage 的 key 或后端 sessionId。
> 知道 key 就能读到那坨数据 —— 所以别把它当鉴权用。

## 4.7 图的变化：审批后接条件路由 + reject 短路

```python
def route_after_approval(state) -> Literal["approve", "reject"]:
    if any(a["action"] == "reject" for a in state.get("approvals", [])):
        return "reject"
    return "approve"

builder.add_conditional_edges("approval_m", route_after_approval, {
    "approve": "deploy_staging", "reject": "finalize",
})
builder.add_conditional_edges("approval_h_lead", route_after_approval, {
    "approve": "approval_h_security", "reject": "finalize",
})
```

H 级的**两段串行**就落在这里：`approval_h_lead` 批准后才走 `approval_h_security`，
任一段 reject 直达 `finalize`。

`finalize` 现在会**自己判断终态**：

```python
rejected = any(a["action"] == "reject" for a in state.get("approvals", []))
outcome = "rejected" if rejected else "released"
```

## 4.8 铁律：`interrupt()` 之前禁止副作用

这是第 4 讲最值钱的一条，是"节点会从头重跑"的直接推论。

| 阶段 | 内容 | 副作用 |
|---|---|---|
| `patch_diff` | submit 入口写入 | 入口做一次 |
| 前序节点 | 只读、校验、分级 | **无** |
| 审批节点 | 只展示 + 收决定 | **禁止**（写文件/发请求/扣款/部署） |
| 部署/切流/写报告 | 审批通过之后 | 放这里（`deploy_staging`/`smoke_test`/`canary_*`/`finalize`） |

一句话：**恢复会重跑代码，但不会撤销已发生的外部操作。**
你部署了两次，不会自动回滚一次。

## 4.9 实测：跨进程恢复（本机跑通）

## 第 4 讲 自测参考答案

**1. 通知会发两次。**
第一次执行 `approval_m` → 发通知 → `interrupt()` 抛出 → 图停。
resume 后节点**从头重跑** → **再发一次通知** → `interrupt()` 返回决定 → return。
更糟的是：如果中间还有部署/扣款，也一样会执行两遍，**而且没人帮你撤销**。
→ 这正是 4.8 铁律的由来。正确做法：通知放到审批通过**之后**的独立节点，
或者给外部请求加**幂等键**（同一个 interrupt_id 只真正发一次）。

**2. 不能过。**
`InMemorySaver` 把快照存在**进程内存**里，进程退出就没了。
AC-4 的场景是"关闭第一个 context，新进程打开同一 SQLite 找回" —— 内存 saver 做不到。
→ 这也解释了为什么第 1～3 讲用 `InMemorySaver` 没问题（都是单进程内跑完），
而第 4 讲必须换 SQLite：**需不需要跨进程，决定了用哪个 saver。**

**3. 三个问题：**
- **体积**：payload 要序列化进 checkpoint（SQLite），几万字符 × 每次中断，DB 迅速膨胀
- **可读性**：审批人要看的是"改了哪几行"，几万字符的 diff 根本没法人工审
- **性能**：`get_state()` / `stream` 每次都要把 payload 反序列化一遍

代码里的 `[:300]` 就是针对性处理 —— 只给预览，要看全的去工单系统。
**同类思路**：凡是"给人看"的数据都要截断，凡是"给机器用"的才存全量。

**4. 不能。**
`thread_id` 只是 checkpointer 的**查找键**，LangGraph 层面对它没有任何鉴权。
谁拿到 `thread_id` 并能调用 `Command(resume=...)`，谁就能替别人做审批决定。
→ 真正的权限必须在**入口层**做：谁有资格批这张工单、这个角色对应哪个 `interrupt_id`，
都要在 `app.py approve` 里自己校验。教材 P19 原文："thread_id 只是查找键，不是权限；
审批权限仍需入口校验。"

**5. 这一讲的能力不够，需要额外的并行机制。**
图上要改：把 `approval_h_lead → approval_h_security` 这条边去掉，
改成两个节点都从 `classify_change` 分出、都汇合到 `deploy_staging`。
**但问题在于**：两个 `interrupt()` 会**串行触发** ——
LangGraph 在一个 superstep 里遇到第一个 interrupt 就停了，第二个根本没机会执行。
想真并行，要么：
- 走 **LangGraph 的并行分支**（同一 superstep 多个节点，需要框架对多 interrupt 的支持），或
- 改成**两个 thread** 各自审批一个人，主线程等两边都回来

→ 教材这里刻意做成**串行**（先 lead 再 security），
因为真实审批流程本来就是"第二个审批人要看到第一个人的结论"，串行更符合业务。
这个题的价值在于让你意识到：**"并行"不是总能加的，要看业务是否真的允许无序。**

# 第 5 讲 · 循环与预算 `demos/05_loops/`（PDF P20–P24）

> 第 4 讲结束时流程是"一条道走到黑"：审批人觉得有问题只能 reject、整单作废；
> 灰度 10% 上去发现错误率飙升，却**没有回滚路径**，只能眼睁睁推到 100%。
> 这一讲加两处循环，并给每处配预算上限防死循环。
> 对应代码：`demos/05_loops/`（state.py 64 / nodes.py 191 / graph.py 113 / app.py 139）

## 5.1 两处循环

| | 循环 A（修订） | 循环 B（回滚） |
|---|---|---|
| 触发 | 审批给 `revise` | `monitor_window` 判不健康 |
| 动作 | `begin_revision` 计数 +1，退回 `intake` 重跑整条链路 | `auto_rollback` 计数 +1，游标回退，重跑同一阶段 |
| 触顶 | 路由判 `stop` → 终止，记 `incomplete` | 路由判 `abort` → 终止，记 `rolled_back` |

教材一句话：**循环让流程可重跑；预算计数防死循环。**

## 5.2 State 新增：预算、游标、采样

```python
# 循环预算（入口提供）
revision_count: int
max_revisions: int
rollback_count: int
max_rollbacks: int
canary_cursor: int        # 灰度游标：0=未开始 1=10% 2=50% 3=100%
```

这一讲把三种 reducer 语义凑齐了，值得对照：

| 字段 | 语义 | 为什么 |
|---|---|---|
| `messages` | `add_messages` | 追加 + 按 id 去重（消息专用） |
| `approvals` / `metric_samples` | `add` | **累计**，审计与监控要保留全部历史 |
| `checks` | **replace**（无 reducer） | 每轮 `collect_checks` 整体覆盖，避免上一轮残留被重复统计 |

**`checks` 用 replace 这个决定很关键** —— 第 3 讲自测第 4 题埋的伏笔在这里回收：
修订循环会回到 `intake` 重跑，如果 `checks` 也用 `add`，第二轮会变成 8 条，
`checks_passed` 变成 8。所以 `begin_revision` 里显式清了：

```python
def begin_revision(state: ReleaseState) -> dict:
    # 只递增计数 + 清空本轮 checks；approvals 是审计，保留累计不清
    return {"revision_count": state["revision_count"] + 1, "checks": []}
```

**`approvals` 故意不清** —— 审计轨迹必须完整，谁在第几轮批了什么，一条都不能少。

另外 `intake` 这一讲不再返回 `stages_completed`（04 里是返回的），
所以修订重跑时 `stages_completed` **不会被清空**，会一直累加。
这是 demo 的一个简化，真工程里通常要在 `begin_revision` 里一起重置。

## 5.3 循环 A：修订（一条普通边指回）

```
intake → 检查 → classify_change → approval_m ──revise──→ begin_revision
   ↑                                   │                       │
   └──────────── 普通边指回 ────────────┼───────────────────────┘
                                       └──approve──→ deploy_staging
```

**循环不需要任何专用 API**，全套就一行：

```python
b.add_edge("begin_revision", "intake")     # 一条普通边，指回已经走过的节点
```

教材方法论：**节点写状态，路由读状态，每圈计数递增 → 路由适时不再选回边。**

## 5.4 循环 B：灰度回滚后原地重试

游标语义：`canary_cursor` 0=未开始，1=10%，2=50%，3=100%。

```python
def auto_rollback(state: ReleaseState) -> dict:
    stage = (state.get("current_stage") or {}).get("stage", "canary")
    return {"rollback_count": state["rollback_count"] + 1,
            "canary_cursor": max(0, state["canary_cursor"] - 1),      # 游标回退
            "stages_completed": state["stages_completed"] + [f"rolled_back:{stage}"]}
```

`max(0, cursor - 1)` 防下溢 —— 游标不会变成负数。

**"原地重试"的算术**：游标 −1 之后，下一圈 `canary_step` 再 +1 → 回到同一个 stage。

### 本机实测：游标逐帧追踪（flaky 服务，max_rollbacks=2）

```
1 submit      cursor=0 rb=0 待批=['INT-1']                            ← 等 Tech Lead
2 resume#1    cursor=0 rb=0 待批=['INT-3-canary_10']       ← canary_step 停在 interrupt
3 resume#2    cursor=0 rb=1 status=unhealthy 待批=['INT-3-canary_10'] ← 回滚，cursor 退回 0
4 resume#3    cursor=1 rb=1 status=healthy   待批=['INT-3-canary_50'] ← 又是 canary_10，这次健康
5 resume#4    cursor=2 rb=1 待批=['INT-3-canary_100']
6 resume#5    cursor=3 rb=1 待批=[]                                   ← released
```

**第 2 行是本讲最值得看的一行**：`canary_step` 已经跑过，`cursor` 算出来是 1，
但提交到 State 的仍是 0 —— 因为 `interrupt()` 在 `return` 之前，游标根本没写进去。

## 5.5 `interrupt()` 在循环里的坑：先算不提交

```python
def canary_step(state: ReleaseState) -> dict:
    cursor = state["canary_cursor"] + 1       # ← 先算，但不提交
    stage = STAGE_BY_CURSOR[cursor]
    decision = interrupt({...})               # ← 停在这
    ...
    return {"canary_cursor": cursor, ...}     # ← 只有 return 时 cursor 才写进 State
```

这是**第 4 讲"节点从头重跑"铁律在循环里的具体应用**：
resume 后节点从头跑，读到的仍是**暂停前的旧游标**（0），重算还是 1，所以**不会重复 +1**。

> 前提仍然是那条：`interrupt()` 之前无副作用。
> 如果 `canary_step` 里在 `interrupt()` 之前写了 `current_stage` 或发了部署请求，重跑时会再来一遍。
> 教材 P24 专门点了这点：**`deploy` 放在审批通过之后。**

## 5.6 预算：为什么 `recursion_limit` 不能替代业务上限

```python
def route_approval(state) -> Literal["approve", "revise", "reject", "stop"]:
    approvals = state.get("approvals", [])
    if not approvals:
        return "stop"
    last = approvals[-1]["action"]
    if last == "approve":
        return "approve"
    if last in ("reject", "abort"):
        return "reject"
    if state["revision_count"] >= state["max_revisions"]:
        return "stop"          # ← 预算耗尽，不再 revise
    return "revise"
```

注意判断**顺序**：先判动作，再判预算。只有确实是 `revise` 且预算还有，才走回边。

| 循环 | 预算字段 | 触顶路由 | 终态 |
|---|---|---|---|
| A 修订 | `revision_count >= max_revisions` | `stop` → `finalize` | `incomplete` |
| B 回滚 | `rollback_count >= max_rollbacks` | `abort` → `finalize` | `rolled_back` |

**`recursion_limit` 是安全阀，不是业务收尾。**
它超限只会抛 `GraphRecursionError` —— 进程崩了，工单状态没落定，报告没写，审计没记。
业务上"最多修订 2 次"必须**自己写成路由**，才能干净地走到 `finalize` 并记 `incomplete`。

## 第 5 讲 自测参考答案

**1. `checks` 会累积成 8 条，`checks_passed` 变成 8。**
因为 `collect_checks` 遍历的是**整个 `messages`**，而 `messages` 用 `add_messages` 是累加的 ——
第二轮跑完，`messages` 里已经有 8 条 `ToolMessage`（第一轮 4 条 + 第二轮 4 条），全都会被解析进 `checks`。
依赖 `checks` 长度的逻辑随即全乱（顶层 `release_pipeline/graph.py` 的 `route_after_checks`
就是读 `checks` 判 `ok`/`blocked` 的）。
→ 这正是"第 3 讲自测第 4 题"预告的那个坑。`checks` 用 replace 就是为了在
`begin_revision` 里显式清一次，让每轮只看到本轮的结果。
（注意：清的是 `checks`，**不是** `messages` —— 消息历史要保留做审计。）

**2. 永远不会 approve。**
`route_approval` 会先在预算那一行就返回 `stop` 或 `revise`，
`if last == "approve": return "approve"` 根本轮不到执行。
表现是：审批人点了 approve，图却走了 stop/revise —— 业务直接错乱。
→ 这和第 2 讲 `classify_change` 的判据顺序是同一类问题：
**规则判断的先后顺序，就是业务决策本身。** 先判"确定性最高的动作"，再判"兜底条件"。

**3. 防下溢。**
如果 `canary_10`（cursor=1）第一次就回滚，直接 `cursor - 1` 得 0，没问题；
但如果游标已经在 0（比如还没开始就异常），`0 - 1 = -1`，
下一圈 `canary_step` 算 `cursor + 1 = 0`，而 `STAGE_BY_CURSOR[0]` **不存在** → `KeyError`。
`max(0, ...)` 把游标钉在 0，保证 `STAGE_BY_CURSOR` 永远能查到合法 stage。
→ 这类"索引/游标回退"的操作，边界钳位是必写的，不是可选防御。

**4. 不能。差别在失败时的表现：**

| | `recursion_limit=25` | 业务预算路由 |
|---|---|---|
| 失败方式 | 抛 `GraphRecursionError` | 走 `stop`/`abort` → `finalize` |
| 工单状态 | **没落定**（outcome 还是 None） | 落定为 `incomplete` / `rolled_back` |
| 报告 | **没写** | 正常写 `finalize` |
| 审计 | 断在半路 | `approvals` 完整保留 |
| 调用方 | 收到异常，要自己兜 | 收到正常返回值 |

→ 一句话：**安全阀是"崩给你看"，业务预算是"体面收尾"。**
生产系统里工单不能凭空消失，所以业务上限必须自己写成路由。

**5. 游标会多走一格，直接跳过一个灰度档。**
- 首次执行：写游标 = 1，然后 `interrupt()` 停
- resume 后从头重跑：读到的游标是 **1**（已被写过），再 +1 = 2
- 结果：跳过了 `canary_10`，直接进 `canary_50`

→ 这就是"**先算不提交**"这个写法的必要性：
让所有状态变更都推迟到 `return` 那一刻，才能保证"重跑 = 幂等"。
教材 P23 原文："`cursor = canary_cursor + 1` 是局部变量，`return` 才写 State → 不会重复 +1"。
**前提：interrupt() 前无副作用。**

## 第 6 讲 自测参考答案

**1. AC-1 不会挂。**
AC-1 断言的是文本里**含节点名**（`intake`/`tool_checks`/`canary_step` 等），
这些跟返回类型无关，照样出现。
真正退化的是**边上的分支标签**（`L`/`M`/`H`/`approve`/`revise`/`retry`…）会消失。
→ 这是"跑通 ≠ 可靠"在本章第四次出现，而且和第 2 讲自测第 3 题是同一件事：
**测试能过，但图的自解释性没了。** 要抓住这种退化，得专门加一条断言边标签的测试。

**2. 两种可能：**
- **停在 `interrupt()`** —— 最常见。此时流里会有 `{"__interrupt__": [...]}` 事件（本讲的情况）
- **根本没走到** —— 前置条件没满足，比如路由没选中它、或者上一个节点报错中断了

怎么区分：
- 看流里有没有 `__interrupt__` 键（有 → 是第一种）
- 用 `get_state(cfg).next` 看接下来要执行的节点是不是它（是 → 说明执行到它了并停下）
- 用 `get_state(cfg).tasks[].interrupts` 看待批内容

→ 排错口诀：**先看 `next`，再看 `tasks.interrupts`，最后才怀疑代码逻辑。**

**3. PNG 生成失败，但 AC-2 不会挂。**
`draw_mermaid_png()` 要联网调 mermaid.ink，离线会抛异常。
但 `export_mermaid` 用 `try/except` 接住了，把异常塞进 `png_status` 字段并返回，
`.mmd` 早在 try 之前就已经落盘。
AC-2 断言的是"`.mmd` 文件存在" + "info 字典含 `png_status` 字段"，两条都满足。
→ 这正是那个降级策略的价值：**最坏情况只是没有图，不会挂掉整个流程。**

**4. 不会崩，但会破坏职责划分。**
`langgraph dev` 宿主会注入自己的内存 checkpointer；如果你在 `studio_graph.py` 里
硬编码了 SQLite saver，dev 环境就会往你的 SQLite 文件里写数据 ——
**开发时用的 DB 和生产 DB 混在一起**，正是教材第 9 章"复用旧 checkpoint 污染测试"的变体。
`build_graph(None)` 的用意就是：这一层只负责"图长什么样"，
checkpointer 这种**环境相关**的东西交给宿主决定。
→ 这就是依赖注入的思路：**核心逻辑不含环境配置。**

**5. 因为 CI 环境不该依赖端口和网络。**
真起 dev server 会带来一串问题：
- 端口 8123 可能已被占用（并行 job 尤其容易撞）
- 需要等启动完成，测试变慢且不稳定
- 要额外装 `langgraph-cli[inmem]`（dev 依赖，不是运行依赖）
- 失败时定位困难（是图的问题还是服务的问题？）

AC-5 只验"`studio_graph.graph` 能 import 且非空" + "`langgraph.json` 配置正确"，
把"能不能加载"和"能不能跑起来"拆开测。
→ 工程原则：**配置正确性可以用单测验，服务可用性该留给集成测试或人工验证。**

## 7.2 坑一：恢复时节点从头再执行 → 副作用重放

| | |
|---|---|
| **现象** | resume 后节点函数从头重跑，不是从 `interrupt()` 那行继续 |
| **原因** | LangGraph 只保存 State 和 checkpoint，**不保存 Python 调用栈** |
| **风险** | `interrupt()` 之前的副作用（部署、写文件、扣款、发消息）会重复执行 |
| **避免** | 副作用放到审批通过后的独立节点；外部请求用**幂等键** |
| **提醒** | **恢复会重跑代码，不会撤销已发生的外部操作** |

顶层代码的落地方式：所有 `deploy` / `rollback` / 写报告都放在审批**之后**，
审批节点本身只做「展示 + 收决定」。

> **幂等键怎么加？** 给每个外部请求带上 `interrupt_id` 或 `ticket_id + cursor` 作为唯一键，
> 服务端收到重复键直接返回上次结果。**这不是 LangGraph 的功能，是业务层必须自己做的。**

## 7.3 坑二：复用旧 checkpoint 污染测试

| | |
|---|---|
| **现象** | 单独跑通过，重复跑或并行跑状态异常（如 `canary_cursor` 停在 1，预期 3） |
| **原因** | 同一 SQLite + 同一 `thread_id`，读到上一轮的旧 checkpoint |
| **避免** | 每会话用干净 checkpoint DB；不同用例用不同 `thread_id`；fixture 清理 |

顶层 `tests/test_acceptance.py` 里有个**教科书级的 fixture**：

```python
@pytest.fixture(scope="session", autouse=True)
def _fresh_checkpoint_db():
    """每个测试会话从干净的 checkpoint 库开始。

    LangGraph 以 thread_id 为坐标持久化整条执行轨迹；如果沿用上一次会话遗留的
    test-checkpoints.sqlite，同名 thread 会从中断处继续，导致"从头跑"的断言失真。
    """
    for p in (Path(os.environ["CHECKPOINT_DB"]), Path(os.environ["REPORTS_DIR"])):
        p = p.resolve()
        if p.is_file():
            p.unlink()
        elif p.is_dir():
            for f in p.glob("*"):
                f.unlink()
    yield
```

注意 `scope="session"` + `autouse=True` —— **不需要任何测试显式引用它**，整个会话自动生效。
这就是"测试不仅要准备输入，也要准备干净的环境"的工程落地。

### 顺带抄一个：把架构约定写成测试

```python
def test_state_schema_closure():
    """AC-7：State 字段闭包检查（防越界）。"""
    from state import ReleaseState
    allowed = set(ReleaseState.__annotations__.keys())
    out = asyncio.run(_drive("AC7", "tiny tweak", [_SRE, _SRE, _SRE]))
    extra = set(out.keys()) - allowed
    assert not extra, f"出现未声明字段: {extra}"
```

**把"闭世界"这个约定变成了自动化检查。** 谁往 State 里塞了没声明的字段，测试立刻红。
这种"把架构约定写成测试"的做法，比写在文档里管用得多。

## 7.4 坑三：`async def` 里的阻塞 I/O 卡住事件循环

顶层代码里有**现成的最优解**，而且作者写了注释解释为什么 —— 整份教材里最值得读的一段：

```python
# 注意：finalize 是 sync 节点。原因：内部 _write_report 用 os.mkdir + Path.write_text，
# 都是同步阻塞 I/O。langgraph dev 的 blockbuster 会拦截 async 节点里的阻塞调用。
# sync 节点由 LangGraph 自动放进 thread pool 执行，不触发拦截。

def finalize(state: ReleaseState) -> dict:      # ← 故意写成 sync
```

顶层 14 个节点的 sync/async 分布，能看出规律：

| 节点 | 定义 | 内部干什么 |
|---|---|---|
| `intake` / `collect_checks` / `classify_change` / `begin_revision` | `def` | 纯计算 |
| `approval_*` | `def` | `interrupt()` |
| `deploy_staging` / `smoke_test` / `canary_step` / `monitor_window` / `auto_rollback` | **`async def`** | `await tool.ainvoke(...)` 真异步 |
| `finalize` | **`def`** | 同步文件 I/O |

**判断规则**（比具体 API 重要）：

- **短同步操作 → 写普通 `def`**，让框架放进线程池
- **真异步 I/O → `async def` + `await`**
- 不得不在 `async def` 里做同步 I/O → `await asyncio.to_thread(...)` 或换 `aiofiles`

教材提醒：**`async def` ≠ 内部操作异步，要逐项检查 I/O 是否阻塞。**

## 7.5 章节小结：六条主线

1. **State 存共享数据**；节点干活并返回增量；边决定下一步
2. **条件路由选路径**，节点执行工作。**先想清业务规则，再映射到节点和边**
3. **并行更新、列表累加要配 reducer**（如 `messages`、审批记录）
4. **`interrupt()` 等人，Checkpoint 保存恢复**；`Command(resume=...)` 送回决定；**恢复时节点从头重跑**
5. **循环必须有业务上限**；`recursion_limit` 只是安全阀，不能替代"最多修订几次"
6. **跑通 ≠ 可靠**：查副作用重放、测试状态隔离、异步 I/O 是否正确

### "跑通 ≠ 可靠"在本章撞了四次

| 次数 | 场景 | 测试全绿，但… |
|---|---|---|
| 1 | 去掉 `add_messages` reducer（第 3 讲实测） | `messages` 从 5 条变 4 条，AIMessage 丢了 |
| 2 | `Literal[...]` 改 `str`（第 2、6 讲） | Mermaid 图的分支标签全没了 |
| 3 | 去掉 `begin_revision` 里清空 `checks`（第 5 讲） | `checks` 累积成 8 条 |
| 4 | `interrupt()` 前放副作用（第 4 讲） | 恢复时执行两遍，且不会撤销 |

## 7.6 AI 辅助 vs 工程师把关（教材 P32–33）

**AI 可以帮你生成**：`state.py`、节点函数、图装配、测试初稿

**工程师必须自己确认的五件事**：

1. **明确边界** —— State 字段、节点、工具，以及**明确不做什么**
2. **定义 AC** —— 覆盖业务规则、**拒绝**、**超限**等边界（不只是正常路径）
3. **检查持久化测试** —— 起点干净，旧状态不影响断言
4. **审查中断前后副作用** —— 恢复重跑不会重复部署/发消息/提交
5. **验证实际运行形态** —— 本地、pytest、服务/Studio **都要验**

教材结语（原文照抄）：

> **AI 把明确结构写成代码；结构是否正确、异常是否安全、结果是否符合预期，由工程师负责。**

## 7.7 这个项目怎么讲（面试表达）

按"讲决策不讲步骤"的框架，这里给四个现成的决策点：

**① 为什么先做主线再叠加机制，而不是一次搭完**
> 六层 demo 每层只加一个机制，每层自带 pytest。出问题时能立刻定位是哪一层的锅。
> 这是可调试性优先的选择。

**② 为什么 `checks` 用 replace 而 `approvals` 用 `add`**
> 这两个字段的业务语义不同：`checks` 是"本轮结果"，修订循环重跑时必须整体覆盖，
> 否则第二轮会累积成 8 条；`approvals` 是"审计轨迹"，谁在第几轮批了什么一条都不能少。
> 同一个 State 里两种 reducer 语义并存，是根据业务语义选的，不是随手写的。

**③ 为什么循环预算自己写成路由，而不用 `recursion_limit`**
> `recursion_limit` 超限只抛 `GraphRecursionError` —— 进程崩了、工单状态没落定、报告没写。
> 生产里工单不能凭空消失，所以业务上限必须自己写成路由，
> 让它干净走到 `finalize` 并记 `incomplete`。

**④ "啊哈时刻"候选**
> 发现 `interrupt()` 恢复时**整个节点会从头重跑**那一刻。它直接改变了我的写法：
> 所有状态变更都推迟到 `return` 那一刻（游标"先算不提交"），所有副作用都移到审批之后。
> **一个框架实现细节，倒逼出一套节点编写规范。**

## 7.8 学习节奏建议

六讲加起来内容不少，但真正的骨架就三句话：

1. **State 是唯一数据通道，节点只报增量**（第 1 讲）
2. **interrupt 会重跑节点，所以 interrupt 前禁止副作用**（第 4 讲）
3. **循环必须配业务预算，跑通不等于可靠**（第 5、7 讲）

其余（条件路由、ToolNode 并行、可视化）都是在这三条骨架上长出来的机制。
