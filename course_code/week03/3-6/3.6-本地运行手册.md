## 一、最重要的一条规则

**每个 demo 必须进到自己的目录里单独跑。**

```
release_pipeline/demos/02_routing/     ← cd 到这里再跑
```

原因：六个 demo 目录下都有**同名**的 `state.py` / `graph.py` / `nodes.py`。
如果在 `release_pipeline/` 根目录跑一条 `pytest` 命令把所有层收进来，
Python 会因为模块名互相覆盖而报错（README 第 7 节明确写了这件事）。

> 记住口诀：**一层一跑，一讲一目录。**

## 五、三个会卡住的坑

**① 在 `release_pipeline/` 根目录跑 pytest**
→ 六个 demo 的 `state.py`/`graph.py` 同名，模块互相覆盖。
✅ 进到具体 demo 目录再跑。

**② 报告文件落在哪里**
`app.py` 里写的是 `Path(__file__).parent / "reports"`，锚定在**文件自身位置**，
所以不管你从哪个目录执行，报告都写到 `demos/02_routing/reports/` 下，不会污染别处。
跑完可以去那个目录翻 `R-02-L.json`，里面有 `change_level` 和 `approver_count` 字段。

**③ 复用了旧的 checkpoint 文件（第 4 讲开始会遇到）**
同一 SQLite 文件 + 同一 `thread_id` 会读到上一轮的旧状态，
表现是「单独跑通过，再跑一次结果不对」。
✅ 每次重跑前删掉 `checkpoints_0X.sqlite`，或换新的 `thread_id`。
（这是教材第九章「三个实际工程问题」之一，第 4 讲会正式讲。）

## 六、动手实验：验证 AC 真的拦得住

光跑通没意义，**故意改坏看测试会不会红**才是真学到了。推荐这一个：

打开 `demos/02_routing/nodes.py`，把 `classify_change` 的判断顺序**人为调换**：

```python
# 原来：敏感词优先
if any(k in lowered for k in ("auth", "payment", "password", "token")):
    level = "H"
elif len(diff) > 800:
    level = "M"
```

```python
# 改成：长度优先（错误顺序）
if len(diff) > 800:
    level = "M"
elif any(k in lowered for k in ("auth", "payment", "password", "token")):
    level = "H"
```

再跑 `python -m pytest tests/ -v`，观察：

- **会不会红？** 会 —— `test_ac3_auth_diff_is_H` 挂掉
- **为什么？** `"modify auth token rotation logic"` 长度约 30 字符，不到 800，
  长度优先时直接命中 `elif` 之前的 `if` 判不到 → 落到 `else` 判成 `L`
- **这正是第 2 讲自测第 1 题的答案**：语法没错、能编译、能跑，但**高危变更被悄悄降级**

改完记得**改回原样**，再跑一次确认 4 passed。

> 同理可以试另一个实验：把 `graph.py` 里 `route_by_level` 的返回类型从
> `Literal["L","M","H"]` 改成 `str`，再跑测试 —— **4 条 AC 全过**，
> 但分支标签在 Mermaid 图里丢了。这就是「跑通 ≠ 可靠」。

## 七、通用模板（以后每讲照抄）

```bash
cd <到具体 demo 目录>
python app.py                    # 先看它怎么跑
python -m pytest tests/ -v       # 再验证 AC
python -m pytest tests/test_xxx.py::test_yyy -v   # 只想看某一条
```

顺序建议：**先 `app.py` 看懂流程，再 `pytest` 验证验收，最后手改源码看会不会红。**
