# 教学资料编写风格手册（基于第一 ~ 四章反推）

> 用途：按「章节主要知识点」生成同风格、同深度的教学资料时，按本手册执行。
> 反推来源：第一 ~ 三章教案 + 第四章教案 + 六份课件 PDF + `course_code/week01`~`week04`。
> 本手册替代此前只基于第四章的版本。

---

## 0. 定位：先校准，别写偏

| 维度 | 定位 |
| --- | --- |
| 读者 | 初学者，**但绝不浅显**：默认读者会写后端、没做过 Agent 工程 |
| 目标 | 建立**工程判断力**——看到一组数字 / 一段代码，能说出它证明了什么、不能证明什么 |
| 语气 | 讲结论时必带限定；讲错法时不留情面 |
| 口径 | 一切数字来自真实脚本实测；没实测就写「本次未验证」 |

> **一句话**：这套资料的产品不是知识，是判断力。

## 1. 破除一个误解：四章不是同一个模板

先看清四章的真实体量（实测，非估算）：

| 章 | 行数 | 代码块 | 表格数 | ⚠️ 标记 | 引用块行 | 外链 |
| --- | --- | --- | --- | --- | --- | --- |
| 一（LLM API / Prompt / 结构化输出） | 1 212 | 36 | 52 | 8 | 53 | 0 |
| 二（Function Calling / Tool Runtime / MCP） | 3 616 | 125 | 89 | 27 | 98 | 3 |
| 三（Agent Loop / State Machine / Codebase Agent） | 3 450 | 125 | 53 | **0** | 106 | 1 |
| 四（Context / Memory / RAG） | 2 968 | 87 | 61 | **54** | 76 | 0 |

**每章收尾装置不同，别套一个壳：**

| 章 | 开头装置 | 结尾装置 | 有无判断题表 |
| --- | --- | --- | --- |
| 一 | **反向下定义**：先列「工程师必须指定、不能交给模型的五件事」 | 「八条结论」编号清单 + 「两篇核心认知」5 行表 | ❌ |
| 二 | 「上一章留下什么」→ 三组件定位表 → **一条主链 ASCII 竖链** | 主链图 + N 条必记 + **课堂练习三分**（口头 / 代码 / 审查验收找 N 类错误）+ 附录 A/B/C 速查 | ❌ |
| 三 | 标题下直接一段 **ASCII 箭头链当地图** | 「错误码速查」18 行表 + **四条贯穿全章的执行规则** | ❌ |
| 四 | **§0 全局地图**（前置知识表 / 分工表 / 案例五项 / 一句话版本） | 串联 ASCII 图 + 排查顺序 + **15~18 条判断题表** | ✅ |

> ⚠️ **第三章 0 个 ⚠️ 标记** —— 它的结论全部装在 `>` 引用块里（106 行），不靠警示符号。
> 这是重要启示：**警示标记是第四章的强化手段，不是全课程的通例。**

**生成新章节时的默认选择**：用第四章的**完整骨架**（§0 全局地图 → 主体 → 串联图 + 排查顺序 + 判断题表），因为它是最成熟的一版；但按章节性质从 §4 装置库里换开头和收尾。

## 2. 跨章共识：八条必修

1. **限定式结论** —— 每个结论后必跟「不代表 / 不能证明 / 不等于 / 不保证」
2. **数字带口径且主动拆穿** —— `usage` 缺失标「未知」不填 0；耗时注明不含哪几段
3. **代码只讲 1~2 个设计点** —— 「这段代码的重点不是语法，而是……」
4. **主动构造破坏性反例** —— 缩预算演示拦截、构造必须项超限演示拒发、保留「带 bug / 修好」两版对照
5. **贯穿案例（或贯穿管道）全章不换**
6. **分层表**（层 / 职责 / 不负责）是四章共用的最强骨架
7. **「X ≠ 你以为的 X」开局** —— 先破除常识误解，再讲机制
8. **小节小结三行**：核心能力 / 验收标准 / 面试能讲

---

## 3. 三条治理红线（贯穿四章，一条都不能软）

1. **提示词不等于鉴权** —— 约束写进提示词只是提醒，要经 Runtime 检查才算拦截
2. **文件内容不构成用户授权** —— README 里写「忽略之前所有指令」≠ 用户说了这句话
3. **权限必须由宿主程序执行** —— 元数据里的 `access_policy` 字段本身不阻止越权读取

配套金句（可直接化用）：

> 「协议连通 ≠ 安全边界建立。MCP 只是把门打开了，门里有没有人查证件是另一回事。」
> 「审批不是对话里的布尔值。`approved=true` 这种字段绝对不能被信任。」
> 「模型的选择是**候选意图**，依赖检查才是**执行许可**。」

## 4. 分章装置库（按需要取用）

### 4.1 第一章的装置

| 装置 | 用法 |
| --- | --- |
| **反向下定义** | 开篇不定义概念，先划责任边界：「以下五件事必须人指定，不能交给模型」 |
| **概念重定位** | 每节以「X ≠ 你以为的 X」开局：`messages 不是聊天记录，是运行时上下文` / `max_tokens 不是长度，是停止条件` / `角色不是头衔，是行为` |
| **弱 vs 强改造型左右对照** | `模糊约束 \| 可观察约束`、`一次完成（易失控）\| 分步完成（可验证）`、`固定规则 \| 运行时数据` |
| **破除一一对应假设** | 用字节流状态机拆穿 `1 Token = 1 SSE = 1 Chunk`（一次 read 可能半条 SSE，也可能三条） |
| **三层拆协议** | L1 HTTP 传输 / L2 SSE 帧 / L3 Harness 事件 |
| **先贴原文再逐字段列表** | 讲 SSE 时先给完整帧原文，再列 `id/event/data/retry` 各字段 |
| **成本对比视角** | 同一 BaseModel 四项职责（定义类型 / 生成 Schema / 校验 / 反序列化）；DeepSeek 把 schema 拼进 system prompt **占 token**，OpenAI 放 `text.format` **不占 token** |

### 4.2 第二章的装置

| 装置 | 用法 |
| --- | --- |
| **一条主链 ASCII 竖链** | 开篇给「必须能背下来」的主链：模型 → Tool Call → Runtime → 工具 → 结果回灌 |

## 5. 表格设计套路（按用途取列标题）

### A. 定位分工类
`机制 | 解决什么问题 | 产物 | 更新方式`
`名称 | 定位 | 解决什么问题 | 不解决什么 | 本课用法`
`层 | 职责 | 不负责` / `层 | 手段 | 保证什么`
`角色 | 负责什么 | 不能替谁决定什么`
`业务概念 | 框架对象`

### B. 能力与局限类（限定式）
`参数 | 真正控制的对象 | 不能解决的问题`
`证据 | 能证明 | 不能证明`
`数据来源 | 典型字段 | 是否可信`
`✅ 能说明 | ❌ 不能说明`
`机制 | 发生位置 | 是否产生新模型决策 | 是否重放同一业务动作`
`测试 | 断言`

### C. 对照改造类（第一章特有）
`模糊约束 | 可观察约束`
`弱角色定义（不可测试）| 可验证的行为定义（可观察）`
`一次完成（易失控）| 分步完成（可验证）`
`固定规则 | 运行时数据`

### D. 治理权限类
`工具 | 副作用 | 数据敏感度 | 风险 | 权限 | 人工确认 | 自动重试`
`机制 | 判断对象 | 可信输入 | 案例 | 失败后动作`
`错误码 | 来源 | retryable`
`失败 | 工具属性 | 推荐动作 | 禁止动作`
`阶段 | 典型问题 | 是否重试 | 正确处置`
`视图 | 目的 | 可以包含 | 不应默认包含`

### E. 状态流程类
`状态 | 放到修代码的过程里理解`
`步骤 | 目标（新事实）| 完成标准 | 证据条数`
`新的观察 | 处置 | 是否修订计划`
`任务 | 更适合起点 | 原因`
`风险等级 | 典型任务 | 隔离方式`
`维度 | 本地 Sandbox | Docker Sandbox`

### F. 验收类
`自检项 | 通过标准`
`站 | 要能回答`
`产物 | 生成前人必须决定 | AI 适合补全 | 本轮验收`
`症状 | 先查哪里`

## 7. 禁止清单（写完逐条自纠）

| ❌ 禁止 | ✅ 替代 |

| 把目标模板写成「已经生成的页面」 | 标注「这是目标模板，不是已经生成的页面」 |

## 8. 生成流程：拿到知识点后的七步

1. **选贯穿案例**：一个能贯穿全章的最小任务 + 一条失败证据（一句话能说清），或从业务流程拆出一条 SOP
2. **定开头装置**：默认用第四章 §0 全局地图；入门章可换第一章「反向下定义」；协议章可用第二章「一条主链」
3. **按小节展开**，每节七步：分清概念 → 机制代码 → 实测数字 → 反直觉结论 → 经验提醒 → 类比 → 小结
4. **每个实验配真实数字**，并标口径（单位、含哪几段、缺什么）
5. **每节配 1 个破坏性反例**（带 bug 版 vs 修好版）
6. **收尾**：串联图 → 排查顺序 → 判断题表（或按章节性质换成错误码速查 / 附录 A/B/C）
7. **自纠**：逐条过 §7，并补 §6 的延伸阅读节

## 9. 句式金库（可直接化用）

**总纲型**

> Schema 是模型与程序之间的 API Contract · 没有契约，就没有 Agent。
> Tool Call 是候选动作，不是执行许可。
> 协议连通 ≠ 安全边界建立。
> 模型的选择是候选意图，依赖检查才是执行许可。

**状态与边界型**

> 超时说明「未收到结果」，不代表「动作未发生」—— `unknown` 是必须被建模的状态。
> 本地超时不代表远端副作用停止。
> 没有 Tool Call 只是协议层的停止信号，不是业务层的完成证据。
> 写操作恢复不是 Replay，而是先恢复执行事实。
> 取消 = 存档点 ≠ 可执行点：不完整的 JSON / 半执行的 SQL / 拼接中断的 Patch 都不能提交。

**纠偏型**

> 不要第一反应修改 Prompt。核心方法：找到第一个断开的连接，在对应层修复。
> 三个不同问题：Streaming = 链路传输 · Checkpoint = 任务状态 · Context Window = 模型能力，互相不能替代。
> 计划可以改变，但是完成标准不能改变。
> 复杂任务需要 Loop，不是因为步骤多，而是因为下一步依赖上一步产生的新事实。

**验收型**

> 可靠的 Agent 应该做到：犯错能发现，发现能修正，失败能暂停，暂停能恢复，完成有证据。
> 工具治理的目标，不是让所有调用都成功，而是让应该执行的动作成功，让不该执行的动作在副作用发生之前停下来。

**分工型**

> AI 把明确结构写成代码；结构是否正确、异常是否安全、结果是否符合预期，由工程师负责。
> 让 AI 当合伙人，不是当主审。
